## שפת התכנון: ״קניון אחד, הרבה חנויות״

המטאפורה נבחרה לכותרת ולמיפוי האחריות: בעל הקניון מנהל תשתיות ושירותים משותפים; בעלי החנויות עצמאיים בתחומם ומתחברים לפי חוזה. זו שפה משותפת, לא החלטה סופית על כל גבול בעלות.

שאלות להכרעה: מה שירות runtime מרכזי ומה חבילה משותפת? מה החנות רשאית לשנות עצמאית? מי מאשר גרסה ומקור קוד? אילו שינויים מחייבים תיאום? מה חוזה השגיאות, ה־context וה־lifecycle?

עצמאות תחומית ופריסה נפרדת כפופות לחוזים ותאימות. אין sandbox מובנה ב־Module Federation או ב־single-spa; remotes באותו דף חולקים סביבת אמון.

## כוונת הדמו והסלוגן

״בונים עם קוד ו־AI. חושבים Enterprise grade״

הדמו העתידי אמור להיות נקודת פתיחה שימושית ומשמעותית ללמידה ולהמשך פיתוח, ולא פלטפורמה ארגונית מוגמרת. הסלוגן הוא כיוון לניסוח ולחשיבה; הוא אינו מוסיף דרישות מימוש, אינו מבטיח יכולות ייצור ואינו משנה את שלב העבודה הנוכחי: תיעוד ותכנון בלבד.

## תפיסת מערכת מתפתחת — פרסום טיוטה אושר

נוסף [מסמך תפיסה פתוח](system-concept.md): מארחי frontend ו־backend מגלים יכולות בקטלוג; אפליקציה יכולה לכלול UI, backend ונתונים; ניתוב מושגי לפי appId+operation. הדימוי dashboard/widgets אינו בחירת UI. טעינה מראש מול לפי צורך, plugin בתוך תהליך מול שירות נפרד, טכנולוגיות backend וגבולות נתונים נשארו פתוחים. אושר תיעוד הכיוון, לא מימוש ולא Blueprint סופי.

## 29.10.2026 — בחירת מנגנון טעינה נשארת פתוחה

הצוות עובד ב־React; אין להסיק משם הריפו שנבחר Module Federation. היעד לניסוי: הוספת אפליקציה שהתפרסמה כשה־Shell כבר פתוח, ללא build/deploy שלו וללא reload מלא. נשווה runtime loader פשוט ל־Federation דינמי, עם קטלוג וחוזים בשתי החלופות. Lazy loading הוא תזמון, Web Components הם חוזה UI אפשרי, ו־Federation הוא מנגנון בין builds; אפשר לשלב. single-spa ו־Web Components נשארים פתוחים. פירוט והוכחות ב־[מסמך התפיסה](system-concept.md). אין מימוש או שינוי שם לריפו.
