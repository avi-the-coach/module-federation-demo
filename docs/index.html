01 / WHY

מה אנחנו רוצים ללמוד?

המטרה

פורטל קטן עם Shell וכמה חלקים עצמאיים, שימחיש כיצד קוד מבילדים נפרדים מתחבר לחוויה אחת. מנגנון הרשאות מדומה קטן יעזור לראות כיצד הקשר משותף משפיע על ניווט ופעולות.

כעת: גוף ידע לקראת Blueprint. הדמו עדיין לא נבנה.

מה לא בונים עכשיו

לא מערכת ייצור, לא התחברות אמיתית, לא ספק זהות, לא שרת הרשאות ולא API עסקי. אין תשלומים אמיתיים, פרטי לקוחות או פריסה של אפליקציות remote.

התרשימים והאינטראקציות כאן מסבירים התנהגות מתוכננת; הם אינם מימוש של Federation.

הבדל חשוב: עצמאות של build ופריסה לא מחייבת repositories נפרדים. אפשר להחזיק הכול ב־monorepo אחד, ועדיין לבנות כל אפליקציה בנפרד.
02 / RESPONSIBILITIES

ארבע שכבות, ארבע אחריויות

Shell

המסגרת שאנחנו כותבים: ניווט, אזור תצוגה, קטלוג מאושר, הקשר משתמש מדומה וטיפול בשגיאות.

מי מחבר את החוויה?

single-spa

אפשרות לתזמור: בחירת אפליקציה לפי מסלול וניהול bootstrap, mount ו־unmount. לא טוען Federation בפני עצמו.

מתי מציגים ומתי מנקים?

Module Federation

טעינת מודולים מבילד אחר בזמן ריצה. חוזה exposes / remotes ומדיניות שיתוף תלויות.

איך מגיע קוד מ־remote?

Webpack

כלי build: אורז קוד ונכסים. תוסף Federation מייצר ומחבר containers. תוצריו רצים בדפדפן.

Monorepo — לא מאגרים מקוננים

מה המבנה כן מאפשר?

מחזור פיתוח משותף וחוזים נגישים, לצד build נפרד לכל אפליקציה. מנהל workspaces, פקודות הרצה ומספר פורטים ייבחרו ב־Blueprint.

אין תיקיות .git פנימיות, אין submodules ואין צורך לפתוח repository לכל חלק.

מה המבנה לא מוכיח?

פריסה עצמאית אינה תוצאה אוטומטית של מבנה תיקיות. נצטרך להוכיח עדכון remote ללא build מחודש של Shell, עם URL/קטלוג תואם וחוזה יציב.

05 / AUTHORIZATION LAB

הקשר מרכזי, לא אשליית אבטחה

הדגמה תיעודית בלבד: החלפת תפקיד משנה את טבלת ההחלטות. אין כאן זהות אמיתית או קריאה לשרת.


המיפוי כאן הוא הצעה להמחשה, לא דרישה עסקית מאושרת.

חוזה אפשרי ל־Shell ול־remotes

getSnapshot() מחזיר הקשר מדומה; can(capability) בודק יכולת; subscribe(listener) מעדכן UI ומחזיר פונקציית ביטול.

ה־Shell יהיה בעל ההקשר ויעביר facade דרך חוזה מוסכם, במקום שכל remote ימציא מצב משתמש משלו. חבילת types משותפת לבדה אינה מבטיחה מופע runtime יחיד.

ב־unmount מבטלים subscriptions. שינוי הרשאה בזמן שהאפליקציה פתוחה צריך להתבטא בלי refresh.

גבול האכיפה: הסתרת כפתור, ניווט חסום או can() בדפדפן הם UX בלבד. במערכת אמיתית השרת מאמת זהות, הרשאה וגישה לאובייקט בכל בקשה. ללא backend, הדמו לא יוכיח אבטחה או מניעת גישה לנתונים.

כל remote באותו דף הוא קוד מהימן בעל גישה לסביבת הדף. Federation ו־single-spa אינם sandbox. ספק קוד לא מהימן דורש דיון נפרד בבידוד.

06 / EVIDENCE, NOT PROMISES

איך נדע שהדמו העתידי עובד?

הוכחה מתוכננתניסויעדות שנשמור
טעינה מבילדים נפרדיםShell ושני remotes; טעינת מסלול שניNetwork: remoteEntry ו־chunks ממקור ה־remote, לא bundling מקומי של כל המסכים
מחזור חיים תקיןמעבר הלוך וחזור עשר פעמיםלוג mount/unmount; ללא DOM כפול או listeners שנשארו
עדכון עצמאישינוי Reports בלבדגרסת remote חדשה מול hash Shell שלא השתנה; גם rollback מתועד
עמידות לכשלעצירת remote אחדה־Shell והאפליקציה האחרת נגישים; fallback מקומי וניסיון חוזר מבוקר
הקשר הרשאות אחידהחלפת תפקיד בעת צפייהניווט ופעולות משתנים יחד, ללא reload; deny כברירת מחדל ליכולת לא מוכרת
תאימות תלויותטעינת שני remotes ושינוי גרסה לא תואמת בניסוי מבוקרמדיניות shared/singleton מתועדת; התנהגות הכשל ודרך התאוששות ידועות

כל השורות ממתינות למימוש. אין בדף זה תוצאות בדיקה של דמו קיים.

07 / DECISION DESK

מה סגור, ומה עוד צריך להחליט?

כיוון מאושר: ידע לפני קוד

מתחילים בתיעוד חזותי ותרשימים; מרחיבים בהדרגה ל־Blueprint. לא מתחילים עכשיו לבנות את הפורטל.

הצעה: Shell + Requests + Reports

שני remotes מספיקים להוכיח טעינה ועדכון עצמאיים. שמות התחומים הם דוגמאות בלבד; אפשר להחליף אותם בלי לשנות את עקרון התכנון.

החלטה פתוחה: האם צריך single-spa בדמו?

בעד: מחזור חיים מפורש ומקום להרחיב תזמור. נגד: שכבה נוספת לדמו קטן. נשווה למסלול Shell + Federation ישיר, ונבחר לפי מה שרוצים ללמד.

החלטה פתוחה: מסלולים, גרסאות וקטלוג

אפליקציה אחת בכל מסלול או כמה אזורים בו־זמנית? כתובות remotes קבועות או קטלוג runtime? איך מאשרים מקור קוד וגרסה, ואיך מחזירים לאחור?

החלטה פתוחה: גבולות ההרשאות

אילו תפקידים ואילו יכולות נחוצים? האם מספיק mock frontend, או שנרצה בשלב עתידי API קטן כדי להוכיח אכיפה? האפשרות השנייה משנה את היקף העבודה ודורשת החלטה נפרדת.

לפני מעבר לביצוע
  1. לבחור שני תרחישים עסקיים זעירים ושמות אפליקציות.
  2. לאשר stack, תזמור, workspaces וגרסאות תואמות.
  3. לסגור חוזי lifecycle, context, routing, CSS וטעויות.
  4. להגדיר פקודות הרצה, בדיקות קבלה וסדר עבודה.
  5. לאשר Blueprint ולהתחיל מימוש רק לאחר מכן.

מקורות והקשר

מפת הידע מעבדת את מסמך הארכיטקטורה שסופק לכדי תכנון דמו מצומצם. בחירות מוצר מסומנות כהצעות; הן אינן דרישות של הספריות.
